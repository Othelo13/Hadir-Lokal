# P2.4 — Attendance integration

The final attendance write uses BEGIN IMMEDIATE and revalidates the live session, active employee, office timezone/date, working day, clock-in/out hours, prior check-in, duplicate, latest cancellation authorization, approved absence and active QR. The server derives identity, status and timestamp. The initial camera challenge is checked before decoding but consumed only in the successful transaction; failed requests no longer burn it. It still expires and is single-use on success. Photo validation remains outside the database lock; a failed insert uses existing photo cleanup. A process crash between photo write and DB commit can still leave an orphan file; operational reconciliation remains release work.

Pending absences do not block attendance. Approved absences block both kinds and retake authorization. Any active record (including rejected selfie) blocks approval. Cancelling an approved absence releases the reservation, not other attendance restrictions. Admin cancellation rechecks live administrator inside its transaction, and retake checks same-day eligibility, current member and latest cancellation, with deterministic rowid tie-breaking and idempotent authorization.

Schedule changes are rechecked at commit. If timezone or office calendar date changes, reject and require reload; other settings are evaluated against current time. Existing attendance rows are not recomputed. No migration added. Tests exercise deterministic service time and existing API tests. Cross-process races and full HTTP/photo workflow testing remain P2.5. Production is unchanged.
